# Architecture

Synroute is a modular monolith. `core` owns task contracts and lifecycle transitions; `repository` discovers a canonical Git root and project hints; `workspace` creates detached worktrees and tracks durable ownership; `sandbox` defines execution types, authorization, and a Docker CLI provider; `verification` runs explicit argv checks only through a configured sandbox; `storage` owns SQLite and repositories; `recovery` performs conservative restart inspection. `execution::coordinator` now persists intent, loads `synroute-verification.json`, creates an owned worktree, and uses the existing lifecycle and event store. The provider-independent `CodingAgent` contract describes events, capabilities, cancellation, output limits, timeout and metadata. It refuses invocation unless an adapter proves isolated execution.

The first adapter identifier is `codex-app-server`, but it is intentionally unsupported. The local Codex App Server exposes experimental stdio JSON-RPC and can execute tools/subprocesses. Synroute's Docker API currently supports bounded one-shot command execution, not a long-lived interactive App Server protocol process. Launching the installed Codex process on the host would permit repository-modifying operations outside Docker. The adapter therefore fails closed. `synroute run` is a coordinator diagnostic entry point, not an end-to-end coding-task feature; it records a failed execution and retains the worktree for inspection when Codex is selected.

## Phase 2 execution boundary

Verification fails closed when an allowed command has no sandbox provider/configuration. Denied, unsupported, and approval-required commands are not executed. Empty contracts are incomplete. Docker uses non-root execution, no network, dropped capabilities, no-new-privileges, read-only root, explicit workspace and temporary mounts, CPU/memory/PID limits, bounded stdout/stderr, timeouts, cooperative cancellation, and label-checked cleanup. See [security.md](security.md) for assumptions and operational limits.

The Docker provider is not a complete host security guarantee. It trusts the local CLI/daemon and host kernel. Git worktrees are not sandboxes. The unsandboxed verification helper has been removed from the public path and cannot execute repository commands directly. Docker execution requires configured SQLite storage. Synroute persists a unique execution-scoped container name and random ownership token before create, then persists a returned ID before start. Unresolved intents and safe cleanup diagnostics remain visible in reports and startup inspection; recovery never performs Docker cleanup.

Docker create and attached start share one monotonic operation deadline and caller cancellation signal. Cleanup receives a separate 15-second grace deadline; session destruction shares one grace deadline across tracked containers. `ExecutionResult` keeps command termination, exit status, bounded output/truncation and execution error separate from cleanup outcome. Verification preserves this evidence and cannot pass when command or session cleanup is unconfirmed. Cleanup resolves a candidate by generated name only, then removes by ID after checking the exact name, managed label, execution ID, and random token label. Durable identity does not prove a container still exists and does not authorize cleanup after restart.

## Coordinator and agent integration

The coordinator uses the existing SQLite execution intent/lease, lifecycle transitions, `PersistentWorkspaceManager`, and trusted `verification::run_for_execution` insertion boundary. It refuses an absent or structurally invalid verification contract. Agent events are append-only `AgentActivity` records. An agent's own completion cannot establish `Completed`. At present the coordinator does not execute the agent or complete verification: Codex is explicitly unsupported because the required long-lived protocol process and its tool subprocess tree are not yet proven to run entirely inside the Docker workload. It retains changed worktrees; normal clean-only workspace removal remains the only automatic removal path.

CLI form: `synroute run <repository> --task "..." [--timeout SECONDS] [--agent codex-app-server] [--json] [--database sqlite://...]`. This command is not a working end-to-end agent integration yet.

## Repository profiler

`repository::profiler` is separate from execution coordination and emits schema-versioned `synroute-profile.json`. It enumerates Git-visible files using `git ls-files --cached --others --exclude-standard`, so standard `.gitignore` rules apply without running repository commands. It omits common generated/dependency directories, binary extensions, common secret filenames, files over 256 KiB, and scans over 32 MiB; profiles at most 1,500 file entries. Classifications are deterministic heuristics with evidence and heuristic confidence, not learned scores. Recommendations are broad model task categories only.

Without provider configuration all analysis is local and deterministic. An optional OpenAI-compatible chat-completions HTTP endpoint can add a short summary. Loopback HTTP endpoints (llama.cpp/LM Studio) are supported directly. A non-loopback HTTP endpoint is rejected unless `--allow-remote` explicitly consents to sending repository paths and structural metadata. API credentials are read from `SYNROUTE_PROFILE_API_KEY` and never serialized or logged. HTTPS is not implemented in this dependency-free transport and is rejected.

CLI: `synroute profile <repository> [--output PATH] [--provider http://127.0.0.1:1234/v1/chat/completions --model MODEL] [--allow-remote] [--json]`. The generated profile can be consumed by future Codex/model-selector integrations; this milestone does not implement routing or benchmarking.

## Persistence, ownership, and recovery

`SqliteStorage` initializes versioned SQLx migrations with WAL, foreign keys, and a 10-second busy timeout. Execution intent, its immutable verification contract, first event, and initial lease are inserted in one transaction. State changes and their events are atomic. Every owner-authorized mutation checks the originating process identity before entering the transaction and validates persisted owner UUID, generation, and unexpired lease inside the mutation transaction. Ownership is create-only: there is no claim/takeover API; a restarted storage instance cannot continue an old execution, and expired leases cannot be renewed. Recovery retires the lease. Terminal state updates are rejected by SQLite. Event sequence allocation serializes through a transaction and a unique `(execution_id, sequence)` index; event rows reject updates and deletes. Execution reports include the persisted verification contract and evidence.

Verification contracts contain unique check names and exact argv, and are immutable after execution creation. Each has a UUID version stored with every evidence report. Only the crate-private `verification::run_for_execution` path can create persistable evidence: it reloads the contract, runs those checks through the independent sandbox-backed verification runner, and then atomically inserts the runner result and event. The API does not accept a caller-constructed `VerificationReport`. Completion requires the latest evidence to match the persisted version and contain exactly one passing result for every required name/argv pair. Migration 0004 adds evidence immutability and insertion-state/contract triggers, and replaces the completion trigger with full contract checks. These database rules protect against accidental and API-level inconsistencies; a user who can directly write the SQLite file can still fabricate matching rows and is outside this trust boundary. The persisted evidence records command identity, exit status, timeout/cancellation, bounded output, and truncation flags; it proves what the trusted in-process runner observed from the configured sandbox provider, not that the command set itself is sufficient for every human acceptance criterion.

Persistent workspaces reserve a database record before invoking `git worktree add`. Initial sidecar creation is exclusive; subsequent sidecar changes verify the previous record and replace it atomically. A local sidecar and the SQLite record hold matching IDs, a random ownership token, canonical paths, and Git administrative/common directory paths. Cleanup checks all three (database, sidecar, and Git registration), then uses the Phase 1 non-forced clean-only removal path. Uncertain or inconsistent metadata refuses cleanup. Migration 0005 persists a bounded workspace uncertainty code and safe diagnostic detail for interrupted or inconsistent states. Startup recovery lists non-removed workspace issues even when their executions are terminal, persists newly discovered reasons, and does not remove uncertain workspaces. This is ownership validation, not a sandbox or a defense against a hostile process running as the same OS user.

All runtime Git subprocesses use `src/git.rs`: inherited environment is cleared (the host PATH is retained to locate the trusted Git executable), system/global config and system attributes are disabled, and command-level overrides disable hooks, fsmonitor, untracked cache, external diff, and interactive diff filters. For worktree commands, repository-configured `filter.*.clean`, `smudge`, and `process` commands are enumerated and overridden with empty commands. Git worktree operations remain host-side and trust the Git binary, host filesystem, and kernel. External merge drivers are not invoked by the current `rev-parse`, `worktree`, or `status` commands; this launcher is not a general-purpose safe wrapper for arbitrary Git commands. Disabling filters can leave files in their stored form or cause repositories that require filters to fail checkout; it does not run those filters on the host.

Every CLI startup first performs read-only inspection of nonterminal executions, their leases, workspace records, and (when Docker is available) matching Synroute-labeled containers. Inspection reports are display data and are not authorization tokens. Applying recovery uses report execution IDs only to select records, reloads the execution and lease from SQLite, and checks liveness from the persisted process markers. A recovery transaction then compares the complete observed lease identity (owner UUID, PID, start ticks, boot ID, heartbeat, expiry, and generation) and observed execution state against current database values before changing state, retiring the lease, appending events, and opening a case. An active owner, a fresh lease, a changed lease, or unknown liveness leaves execution state untouched. On non-Linux systems or when process identity cannot be read, liveness is unknown and recovery fails closed.

The default lease is 45 seconds. Owners must call `renew_lease` periodically (recommended every 15 seconds); the API caps requested TTL at 300 seconds. There is no execution coordinator or background heartbeat task yet, so this is a persistence/recovery primitive that future execution code must actively renew. Leases use UTC wall-clock expiry; forward changes may shorten the apparent lease and backward changes may delay recovery, but owner inactivity is independently required. Recovery never resumes execution or removes workspaces/containers. Uncertain ownership is recorded as an open recovery case without changing lifecycle state. Open cases repeat in startup reports until acknowledged or resolved, and remain queryable afterward. Runtime label matches identify candidates but do not prove historical provenance.

`RecoveryRequired` means liveness or ownership cannot be established automatically and a human must inspect the report before deciding how to proceed. This state is terminal to prevent accidental continuation through normal lifecycle transitions.
