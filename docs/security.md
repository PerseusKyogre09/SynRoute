# Sandbox security boundary

## Implemented boundary

Repository profiling is local by default. It enumerates Git-visible files with Git's standard ignore rules, excludes common sensitive filenames and binary/generated paths, and does not put file contents into the LLM prompt. A provider must be explicitly configured; non-loopback endpoints additionally require `--allow-remote`, which sends file paths and structural metadata. `SYNROUTE_PROFILE_API_KEY` is used only as an HTTP Authorization header and is excluded from generated JSON and diagnostics. The built-in transport supports plain HTTP only; use loopback endpoints unless remote transfer is intentionally approved. Plain HTTP remote endpoints are not suitable for secrets in transit; use only trusted networks or configure a future TLS-capable transport.

The Phase 4 coordinator and provider-neutral adapter contract are present. The Codex adapter is deliberately unsupported and fails closed. Codex App Server uses a documented stdio JSON-RPC protocol, but the current Docker provider only supports one-shot `docker create` plus attached execution/removal; it has no persistent bidirectional stdin/stdout session. No Codex runtime image or runtime wiring is configured. A Git worktree does not constrain tools, and the existing one-shot sandbox API cannot host the persistent server.

Authentication is a second blocker. OpenAI's documented Sign in with ChatGPT flow passes an OAuth access token to the App Server as `ACCESS_TOKEN`, which is sent as a bearer token to `/v1/responses`. The App Server and its agent tools share a process environment, so repository-controlled or agent-launched child processes could read that token. Synroute has no Sign in with ChatGPT implementation, scoped token broker, or outbound allowlisting proxy. Mounting `~/.codex`, forwarding `OPENAI_API_KEY`, or injecting a broad bearer credential is not an acceptable workaround. A future integration needs an independently reviewed broker that limits destination, method, model/usage scope and token lifetime while keeping the raw credential outside the agent-visible process, plus a network path restricted to that broker. See [Codex App Server token-sharing instructions](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) and [Sign in with ChatGPT credential model](https://developers.openai.com/siwc/token-sharing-open-source).

No host Codex invocation, credentials mount, sandbox weakening, or claim of sandboxed Codex execution is made. The current environment also cannot access the Docker daemon (`permission denied` on `/var/run/docker.sock`), so persistent attach, cancellation, container termination and runtime image behavior could not be exercised here.

Repository verification is routed through `SandboxProvider`; there is no host-process fallback. The policy matches exact executable names and returns allowed, denied, approval-required, or unsupported. Only allowed structured argv commands are submitted. Empty verification contracts return `incomplete`, never success. The provider API accepts explicit environment variables, per-command timeouts, resource limits, bounded output, and a cancellation signal.

The Docker provider uses the installed Docker CLI as a structured host control interface and requires configured SQLite storage. Before create, it persists a unique execution-scoped name and random ownership token; after create it persists the returned ID before start. It runs the requested executable and arguments directly (no shell construction by Synroute). Cleanup can use the name only to find candidates; it removes by ID after verifying the exact name, managed label, execution ID, and random token label. Cancellation or timeout kills the attached Docker CLI and requests forced removal only after these checks. Normal completion uses non-forced removal. Ambiguous create outcomes trigger exact-name candidate lookup followed by full label verification. Daemon/list/inspection/cleanup uncertainty leaves a durable open intent and safe diagnostic for manual inspection; no resource is removed by name alone.

Create and attached start share one monotonic absolute operation deadline, and the caller cancellation signal reaches both. Cleanup has a separate 15-second grace deadline; session destruction shares one grace deadline across tracked containers. Results preserve exit status, timeout/cancellation, stdout/stderr and truncation independently from cleanup status and whether the container may remain. Verification cannot pass if command or session cleanup is unconfirmed.

Container settings include a non-root numeric UID/GID, `--network=none`, all Linux capabilities dropped, `no-new-privileges`, read-only container root, an explicitly writable workspace bind mount, a bounded noexec `/tmp` tmpfs, CPU/memory/PID limits, and Docker's default seccomp profile. Only explicitly configured environment variables are passed. No Docker socket or unrelated host paths are mounted.

## Authorization and usage

The policy is a command-level gate, not a proof that an allowed program's arguments are safe. A permitted build tool can execute repository build scripts inside the container. Policies should be configured for the task and trust level; approval-required commands remain skipped until approval is explicitly supplied. Repository-discovered hints are not executed automatically. Agent-generated shell strings are not accepted by this interface.

Verification stdout and stderr are bounded but persisted verbatim in evidence. This milestone does not redact credentials from task descriptions or output; verification commands should not print secrets until a separate redaction design is implemented.

To opt into the real Docker integration test, set `SYNROUTE_DOCKER_IMAGE` to an already available image that contains `sh` and run:

```sh
SYNROUTE_DOCKER_IMAGE=your-image cargo test docker_integration -- --ignored --nocapture
```

The integration test is ignored during the ordinary suite so tests do not unexpectedly contact a daemon or pull an image.

## Assumptions and limitations

The Docker CLI and daemon are trusted, local host components. Access to a rootful Docker daemon is effectively host-privileged; a compromised daemon, kernel, or container runtime can defeat this boundary. Docker containers share the host kernel and are not a complete defense against kernel vulnerabilities or all side channels. Prefer a rootless Docker daemon where operationally suitable. The selected image must be trusted and available locally; Synroute does not pull images. Linux container support is assumed.

The operation timeout includes Docker create plus attached start. Cleanup can extend total wall-clock time by up to its separate grace period. Cancellation is cooperative through the provided receiver; aborting the Rust task may leave an unresolved intent for manual inspection. Intent records preserve name/token/ID data across restart and are shown by recovery inspection, which does not remove containers. A persisted intent is not proof that the container exists; it may represent an interrupted create that never took effect.

## Host-side Git behavior

Repository discovery and workspace management still run the trusted host Git executable. Every runtime Git subprocess goes through `src/git.rs`, which clears inherited environment variables except PATH (and `SystemRoot` on Windows), ignores system/global Git configuration, disables system attributes, and applies command-line overrides for `core.hooksPath`, `core.fsmonitor`, untracked cache, external diff, and interactive diff filters. The hooks path is a unique private empty directory. Worktree operations enumerate local/included `filter.*` config keys and override each configured clean, smudge, and process command with an empty command. A filter-required checkout may fail; configured filters are not executed to produce filtered working files. Workspace validation and cleanup failures are stored as bounded reason codes and fixed safe details. Recovery reports list non-removed workspace issues independently of execution state, including workspaces attached to terminal executions; they do not remove those workspaces.

These settings prevent Git hooks, fsmonitor, external diff commands, and repository-configured clean/smudge/process filters from running in Synroute's current Git operations. Current commands are limited to `rev-parse`, `status`, `worktree list`, `worktree add`, and non-forced `worktree remove`; they do not perform merges, so configured merge drivers are not invoked. This is not a general safe-Git wrapper and does not sandbox Git: the executable found via host PATH, Git itself, the host filesystem, and kernel remain trusted. Do not add arbitrary Git subcommands without reviewing their helper behavior and extending this isolation.

## Durable execution ownership and recovery

Execution creation records the immutable verification contract, owner lease, execution intent, and creation event atomically. A storage instance has a random owner UUID and generation 1. Ownership acquisition is create-only: no lease transfer or takeover exists, and reopening storage after restart does not authorize the new instance to continue the old execution. Every owner-authorized mutation checks the originating process identity before entering the transaction and validates owner UUID/generation plus an unexpired lease in the same database transaction. Expired leases cannot be renewed. On Linux the lease records boot ID, PID, and `/proc/<pid>/stat` start ticks; this detects ordinary PID reuse but is not a persistent kernel process handle. The default lease duration is 45 seconds and renewal caps leases at 300 seconds. No background heartbeat exists because the execution coordinator is not implemented; future long-running execution must renew periodically.

Startup inspection is read-only. Recovery uses report IDs only as lookup hints; it reloads execution and lease fields from SQLite and evaluates liveness from those persisted process markers. The recovery transaction compares owner UUID, PID, start ticks, boot ID, heartbeat, expiry, generation, and observed execution state before atomically recording `RECOVERY_REQUIRED`, retiring the lease, appending events, and opening a recovery case. A caller-altered report cannot authorize recovery of a live persisted owner. If owner liveness is unknown, or the platform cannot provide process identity, Synroute stores an open uncertainty case and leaves execution state and lease untouched. No recovery path resumes work or deletes a workspace/container.

Each execution persists an immutable verification contract of unique check names and exact argv, bound to a version UUID. Evidence is stored only through the crate-private runner path, which loads that contract and records actual sandbox runner results. SQLite rejects evidence outside `VERIFYING`, contract/version or check-set mismatches, evidence updates/deletes, and completion unless the latest report has one passing result per required check. Evidence records observed command identity, exit status, timeout/cancellation, bounded output, and truncation. This proves what the trusted in-process runner observed from its configured sandbox provider; it does not prove that the chosen checks are sufficient for every human acceptance criterion. The boundary assumes Synroute and the configured provider are trusted. It does not protect against a user with direct write access to SQLite, who can forge rows or alter the schema.

Open recovery cases are included on each startup report until acknowledged or resolved. Acknowledged and resolved cases remain queryable as history. This design assumes local Linux `/proc` identity and wall-clock lease expiry; a forward clock change can make a lease appear expired earlier and a backward change delays recovery. Expiry alone never authorizes recovery; owner inactivity is independently required. Non-Linux or inaccessible process data fails closed. It does not prove that an active process is making progress, so an expired lease with a live owner is reported for manual review.

## Docker references

The implementation uses Docker's documented container-create options for resource constraints, read-only root filesystems, dropped capabilities, no-new-privileges, and network selection: [container create reference](https://docs.docker.com/reference/cli/docker/container/create/) and [container run reference](https://docs.docker.com/reference/cli/docker/container/run/). Docker documents that access to a rootful daemon is highly privileged; see [Docker Engine security](https://docs.docker.com/engine/security/) and [rootless mode](https://docs.docker.com/engine/security/rootless/).
